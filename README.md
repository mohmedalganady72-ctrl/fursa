## نظرة عامة

**منصّة الفٌرص** هي تطبيق ويب متكامل (Full-stack) يحل مشكلة تشتت فٌرص العمل والتطوع والتدريب التعاوني بين قنوات متفرقة (منشورات سوشال ميديا، مجموعات واتساب، مواقع متفرقة)، ويستبدلها بمكان واحد منظّم يجمع:

- **الباحثين عن فٌرصة**: خريجون، طلاب، وأي شخص يبحث عن عمل أو تطوع أو تدريب تعاوني.
- **الجهات**: شركات، مؤسسات، ومنظمات تطوعية تُعلن عن فٌرصها وتدير المتقدمين عليها.
- **مدير المنصة**: يشرف على اعتماد الجهات، مراجعة المحتوى، ومتابعة صحة المنصة العامة.

الميزة الجوهرية التي تميّز المنصة عن أي لوحة إعلانات وظائف تقليدية هي **الترتيب الذكي للمتقدمين**: بدلًا من أن تغرق الجهة في مئات الطلبات بلا ترتيب، يحسب النظام درجة توافق (Compatibility Score) لكل متقدم بناءً على معايير موزونة تختلف حسب نوع الفٌرصة (عمل / تطوع / تدريب تعاوني) — وهذا **ترتيب إرشادي فقط**، القرار النهائي يبقى دائمًا بيد الجهة.

> 📄 هذا الـ README يغطي الصورة العامة والهيكلة. الوثيقة التفصيلية الكاملة (حالات الاستخدام، حقول كل نموذج، المخاطر التقنية، خطة الفريق) موجودة في [`docs/requirements-and-design.md`](./docs/requirements-and-design.md).

## الفئات المستهدفة والأدوار

| الدور | الوصف المختصر | مساره في `app/` |
| --- | --- | --- |
| **زائر (Guest)** | يتصفح الصفحة الرئيسية فقط دون تسجيل دخول | `app/(public)` |
| **باحث عن فٌرصة (Applicant)** | يبحث، يقدّم، يتابع حالة تقديماته، يتحدث مع الجهات | `app/(applicant)` |
| **جهة (Organization)** | تنشر فٌرصًا، تستقبل وتُقيّم المتقدمين، تقبل/ترفض | `app/(organization)` |
| **مدير المنصة (Admin)** | يعتمد الجهات، يراقب المنصة، يرسل إشعارات عامة | `app/(admin)` |

## الميزات الرئيسية

- 🔍 **بحث وفلترة**: بحث نصي (اسم الجهة / عنوان الفٌرصة / التخصص) + فلاتر (المنطقة، التخصص، نوع الدوام) + ترتيب (الأنسب، الأقرب لانتهاء التقديم، الأقل/الأكثر تقدمًا).
- 🧠 **بحث ذكي**: رفع السيرة الذاتية (PDF) → استخراج تلقائي للمهارات والخبرات → مطابقتها مع الفٌرص المتاحة.
- 📊 **ترتيب ذكي للمتقدمين**: درجة توافق مئوية لكل متقدم لكل فٌرصة، بأوزان مختلفة حسب نوع الفٌرصة.
- 🔔 **إشعارات ذكية**: داخل النظام + بريد إلكتروني، بما فيها تنبيهات سلوكية (رسالة تحفيزية عند عدم الدخول 3 أيام).
- 💬 **دردشة مباشرة**: بين الجهة والمتقدم المقبول فقط، عبر Supabase Realtime.
- ⏱️ **إغلاق فوري وذري**: فور قبول العدد المطلوب من المقاعد، تُغلَق الفٌرصة تلقائيًا (معاملة ذرية تمنع تجاوز عدد المقاعد عند طلبات متزامنة) وتُرفَض بقية التقديمات المعلَّقة تلقائيًا — لا مهلة انتظار، القبول نهائي فور اتخاذه.
- 📝 **سجل تدقيق كامل**: كل تغيير في حالة تقديم، وكل إجراء إداري حساس (اعتماد جهة، إنشاء مدير، إشعار جماعي)، يُسجَّل في سجل تاريخي دائم (Audit Log) لا يُحذف ولا يُعدَّل.
- 🔒 **لا تعديل بعد النشر**: الفٌرصة المنشورة ثابتة البيانات؛ أي تغيير جوهري يُغلق الفٌرصة الحالية وينشئ فٌرصة بديلة، حفاظًا على العدالة بين المتقدمين.
- 🔐 **خصوصية مضبوطة**: المتقدمون يرون بعضهم (اسم وصورة فقط)، ولا يستطيعون فتح ملفات بعضهم؛ الجهة وحدها ترى التفاصيل الكاملة.
- 📱 **تصميم متجاوب بالكامل**: تجربة مصمَّمة أولًا للهاتف (Mobile-first)، تمتد بسلاسة للآيباد والكمبيوتر.

## التقنيات المستخدمة (Tech Stack)

تم اختيار كل تقنية بناءً على ثلاثة معايير: **تكلفة مبدئية صفرية**، **توحيد لغة البرمجة (TypeScript)** لتسهيل التنسيق بين 7 أفراد، و**سهولة النشر على Vercel**.

| الطبقة | التقنية | لماذا |
| --- | --- | --- |
| الاستضافة | **Vercel** | نشر مباشر من Git، SSL تلقائي، خطة مجانية كافية |
| إطار العمل | **Next.js 15 (App Router)** | يدمج الواجهة والـ API في مشروع واحد |
| قاعدة البيانات | **Supabase (PostgreSQL)** | علائقية + مرتبطة أصلًا بالتخزين والـ Realtime |
| ORM | **Drizzle** | خفيف، سريع على serverless، type-safe بالكامل |
| المصادقة | **Better Auth** | يدعم الأدوار المتعددة (باحث/جهة/مدير) بمرونة |
| تخزين الملفات | **Supabase Storage** | لملفات CV، الصور الشخصية، شعارات الجهات |
| الدردشة الفورية | **Supabase Realtime** | قنوات WebSocket جاهزة دون خدمة خارجية |
| البحث النصي | **PostgreSQL + pg_trgm** | بحث تقريبي (fuzzy search) بدون محرك بحث خارجي |
| المهام المجدولة | **pg_cron** (داخل Supabase) | إنهاء الفٌرص عند انتهاء موعدها والتنبيهات السلوكية — مجانًا |
| البريد الإلكتروني | **Nylas** | إرسال أكواد التحقق والإشعارات (Transactional Send) |
| الواجهة (UI) | **Tailwind CSS + shadcn/ui** | بناء سريع، تحكم كامل بالتصميم، يدعم RTL |
| الرسوم البيانية | **Recharts** | لوحات إحصائيات الباحث/الجهة/المدير |
| التحقق من الصحة | **Zod** | للتحقق من مدخلات النماذج والـ API |
| الاختبار | **Vitest + Playwright** | اختبارات وحدة + اختبارات طرفية (E2E) |
| المراقبة | **Sentry (خطة مجانية)** | تتبّع الأخطاء في بيئة الإنتاج |

**لماذا لا يوجد Vector Search (pgvector) في الإصدار الأول؟**
البحث الذكي هنا هو ترشيح بنيوي (Structured Matching) بأوزان ثابتة معلومة مسبقًا — يُحسب بكفاءة عبر SQL عادي دون الحاجة لتضمين متجهي (Embeddings). يُضاف لاحقًا فقط إذا ظهرت حاجة فعلية لمطابقة نصية دلالية أعمق.

## نمط الهيكلة ولماذا اخترناه

اعتُمد نمط **Feature-based / Domain-Driven Structure** (الهيكلة حسب المجال الوظيفي)، وليس نمط "Type-based" التقليدي (مجلد واحد ضخم لكل الـ `components`، ومجلد آخر لكل الـ `services`، إلخ). هذا قرار مقصود وليس اعتباطيًا، وله ثلاثة أسباب مباشرة:

1. **يطابق تقسيم الفريق تمامًا.** وثيقة المتطلبات قسّمت فريق الـ7 أفراد حسب المجالات (الفٌرص والبحث، التقديمات والترتيب الذكي، الحسابات، الإشعارات والدردشة، لوحة المدير...). مجلدات `features/*` هي نفس هذا التقسيم حرفيًا — كل عضو فريق يعرف بالضبط أي مجلد هو "منطقته"، وتعارضات الـ Git تقل بشكل كبير لأن كل شخص يعدّل ملفات في مجلد مختلف.

2. **يفصل "أين تُعرض الصفحة" عن "كيف يعمل المنطق".** مجلد `app/` يبقى **رقيقًا جدًا** (routing فقط — أي صفحة تستورد من `features/` وتُركّب المكوّنات)، بينما منطق الأعمال الفعلي (خوارزمية الترتيب، تحليل CV، دورة حياة القبول) يعيش في `features/*/services`. هذا يعني أن أي منطق يمكن اختباره واستدعاؤه من أي مكان (صفحة، API route، cron job) دون تكرار الكود.

3. **يمنع "مجلد God" لا أحد يجرؤ يلمسه.** النمط التقليدي (`components/`, `hooks/`, `services/` عامة لكل المشروع) ينتهي دائمًا بملفات ضخمة مبعثرة بلا حدود واضحة مع نمو المشروع. تقسيم كل مجال إلى `components/ hooks/ services/ validators/` خاصة به يبقي كل جزء صغيرًا ومحكمًا.

**القاعدة الذهبية:** لو الملف يخص ميزة واحدة محددة (نموذج إعلان فٌرصة، خوارزمية التوافق) → مكانه `features/<اسم-المجال>/`. لو الملف عام يُستخدم عبر ميزات متعددة (زر، Header، دالة تنسيق تاريخ) → مكانه `components/` أو `lib/` أو `hooks/`.

## شرح كل مجلد رئيسي

### `app/` — طبقة العرض فقط

مقسّم إلى **Route Groups** بحسب الدور: `(public)` `(auth)` `(applicant)` `(organization)` `(admin)`. كل مجموعة لها `layout.tsx` خاص يتحقق من الصلاحية المناسبة قبل عرض أي صفحة داخلها. الصفحات نفسها **لا تحتوي منطق أعمال** — فقط تستورد من `features/` وتعرض المكوّنات.

### `features/` — منطق الأعمال (القلب الحقيقي للمشروع)

كل مجلد فرعي هنا مستقل قدر الإمكان ويحتوي بنية موحّدة:

```
features/<اسم-المجال>/
├── components/    # مكوّنات UI خاصة بهذا المجال فقط
├── hooks/         # React hooks خاصة بهذا المجال
├── services/       # منطق الأعمال واستعلامات قاعدة البيانات (Drizzle)
├── validators/      # مخططات Zod للتحقق من المدخلات
└── types.ts          # أنواع TypeScript خاصة بهذا المجال
```

### `components/` — مكوّنات واجهة عامة فقط

أي مكوّن هنا يجب أن يكون **بلا معرفة بمنطق الأعمال** — يستقبل بيانات عبر props ويعرضها فقط. مثال: `OpportunityCard` يعرض بيانات فٌرصة أُرسلت له، لكنه لا "يعرف" من أين جاءت هذه البيانات.

### `lib/` — الأساسات المشتركة

إعدادات لا تتغيّر حسب الميزة: اتصال قاعدة البيانات، عميل Supabase، إعداد المصادقة، الثوابت العامة.

### `db/` — كل ما هو SQL خام خارج Drizzle

مهام `pg_cron` وسياسات `RLS` تُكتب كملفات `.sql` صريحة هنا (وليست مخفية داخل الكود) حتى يسهل مراجعتها أمنيًا بشكل مستقل، وتُطبَّق يدويًا أو عبر سكربت نشر على Supabase.

## نظام التصميم (Design System)

> 🎨 هذا القسم يوثّق **القرارات التصميمية**، وسيُستكمل بتفاصيل بصرية أدق (الألوان الدقيقة، سلّم المسافات، مكتبة الأيقونات) في ملف `docs/design-system.md` مستقبلًا.

### المبادئ الموجّهة

- **Mobile-first إلزامي**: كل مكوّن يُصمَّم أولًا لعرض 375px، ثم يُوسَّع تدريجيًا (`sm:` `md:` `lg:` `xl:`) — وليس العكس.
- **RTL أصيل لا مُسقَط**: الاتجاه من اليمين لليسار جزء من بنية التصميم نفسها (`dir="rtl"` على مستوى `<html>`)، وليس تعديلًا لاحقًا فوق تصميم LTR جاهز.
- **تناسق عبر Design Tokens**: كل الألوان، المسافات، وأحجام الخطوط تُعرَّف كمتغيرات CSS في `app/globals.css` ويُعاد استخدامها عبر إعدادات Tailwind — ممنوع كتابة قيم لون/مسافة حرفية متفرقة داخل المكوّنات.
- **هوية بصرية غير نمطية**: تفادي "القالب الجاهز" المتوقع في كل موقع عربي مشابه؛ الاعتماد على تركيبة ألوان وطباعة مدروسة خصيصًا للمنصة (تُحدَّد لاحقًا في جلسة تصميم مخصصة).
- **حالات واضحة لكل تفاعل**: Loading / Empty / Error / Success لكل شاشة رئيسية (لهذا يوجد `loading-skeletons.tsx` و `empty-state.tsx` كمكوّنات مشتركة من اليوم الأول).

### مكوّنات الأساس (shadcn/ui)

تُستخدم shadcn/ui كطبقة أساس (Accessible by default عبر Radix UI) ثم تُخصَّص بصريًا بالكامل عبر Tailwind — النتيجة مكوّنات ذات سلوك موثوق (Accessibility, Keyboard Navigation) لكن بهوية بصرية خاصة بالمنصة وليست "افتراضية".

### دليل الصور المطلوبة للمشروع

كل مكان في الكود يحتاج صورة سيحمل تعليقًا يوضّح: **الوصف، المقاس المقترح، الصيغة، وأي ملاحظة تصميمية**. مثال على الصيغة المتبعة (ستجدها لاحقًا داخل ملفات المكوّنات نفسها):

```tsx
{/* 
  صورة: شعار المنصة (نسخة أفقية للهيدر)
  المقاس المقترح: 160×40px (نسبة 4:1) — SVG يُفضَّل، أو PNG شفاف بدقة 2x (320×80px)
  الصيغة: SVG (أولوية) أو PNG بخلفية شفافة
  ملاحظة: يجب أن يعمل بوضوح على خلفية فاتحة وداكنة (نسختان أو لون قابل للتحكم عبر currentColor)
*/}
```

الفئات المتوقعة للصور عبر المشروع:

| الفئة | أمثلة مواضعها | المقاس التقريبي | الصيغة المقترحة |
| --- | --- | --- | --- |
| هوية بصرية (شعار) | Header, Footer, صفحة الدخول | 160×40px أفقي / 40×40px أيقونة | SVG |
| رسوم توضيحية (Illustrations) | الصفحة الرئيسية، الحالات الفارغة | 400×400px تقريبًا | SVG أو PNG شفاف |
| صور شخصية (Avatars) | ملف الباحث، بطاقات المتقدمين | 96×96px يُخزَّن / حتى 200×200px يُعرَض | WebP أو JPEG مربعة 1:1 |
| شعارات الجهات | ملف الجهة، بطاقة الفٌرصة | 128×128px مربع | PNG شفاف أو WebP |
| صور غلاف (Hero) | الصفحة الرئيسية | 1600×900px نسبة 16:9 | WebP مضغوطة |
| أيقونات الواجهة | كل مكان (أزرار، حالات، تنقل) | 20×20px أو 24×24px | مكتبة `lucide-react` (SVG برمجي) |

> **قاعدة عامة:** أي أيقونة وظيفية متكررة تُستخدم من مكتبة أيقونات (`lucide-react`) بدلًا من ملفات صور منفصلة — توفيرًا للحجم وسهولة لتغيير اللون. الصور الفعلية (رفعات المستخدمين، الرسوم التوضيحية) فقط هي ما يُخزَّن كملفات في `public/images/` أو Supabase Storage.

## خوارزمية الترتيب الذكي

لكل نوع فٌرصة أوزان مختلفة لحساب درجة التوافق (Score = مجموع درجة كل معيار مضروبة بوزنه):

**فٌرص التطوع** — المجالات 40% · المهارات والخبرات 30% · المدينة 15% · الوصف والنبذة 10% · الجنس عند الشرط 5%

**التدريب التعاوني** — التخصص 40% · الجامعة والمتطلبات الأكاديمية 15% · المستوى الدراسي 15% · المجالات 15% · المدينة 10% · الوصف والنبذة 5%

**فٌرص العمل** — التخصص والمجال 30% · المهارات المطلوبة 25% · الخبرة 20% · معلومات مستخرجة من CV 10% · المؤهل 10% · المدينة 5%

منطق الحساب موجود في `features/matching/services/scoring-engine.ts` وجداول الأوزان في `features/matching/services/scoring-weights.ts` — **مفصولة عمدًا** حتى يسهل تعديل الأوزان دون لمس منطق الحساب نفسه.

**تنبيه مهم في الكود والواجهة:** هذه الدرجة **إرشادية فقط**، والواجهة يجب أن تُظهر ذلك بوضوح للجهة (مثلًا عبر نص توضيحي أعلى قائمة المتقدمين) — القرار النهائي بالقبول أو الرفض يبقى بيد الجهة دائمًا.

## دورة حياة التقديم

```
تقديم الباحث (applied)
     │
     ▼
الجهة تراجع (under_review) ← قد تُرشِّحه مبدئيًا (shortlisted) اختياريًا
     │
     ▼
قرار الجهة
     │
     ├── قبول ──▶ معاملة ذرية واحدة:
     │            1. زيادة seatsFilled (بشرط توفر مقعد ضمن نفس الاستعلام — يمنع تجاوز العدد عند طلبات متزامنة)
     │            2. حالة التقديم ← accepted (نهائي، لا مهلة انتظار)
     │            3. إنشاء محادثة فورية بين الجهة والمتقدم
     │            4. إن اكتمل عدد المقاعد المطلوب ← الفٌرصة تُغلَق فورًا (closed)
     │               وكل التقديمات الأخرى غير المبتوت فيها ← closed تلقائيًا
     │
     └── رفض ──▶ rejected (فوري ونهائي)

الباحث يستطيع سحب طلبه بنفسه في أي وقت قبل القبول ← withdrawn
```

كل تغيير حالة (بما فيها الإغلاق التلقائي الجماعي) يُسجَّل في `application_status_history` — سجل تاريخي دائم لا يُحدَّث، فقط يُضاف إليه (راجع `lib/db/schema/application-status-history.ts`).

بالتوازي: عند بلوغ **آخر موعد للتقديم** المحدَّد في الفٌرصة دون اكتمال المقاعد، تنتقل الفٌرصة لحالة `expired` تلقائيًا (مهمة `pg_cron` منفصلة — مختلفة عن `closed` التي تعني تحديدًا اكتمال القبول أو استبدال الجهة للفٌرصة).

> **لا يوجد تعديل لفٌرصة بعد نشرها.** أي تغيير جوهري مطلوب يمرّ عبر `POST /api/opportunities/:id/replace`، الذي يُغلق الفٌرصة الحالية (تبقى كسجل تاريخي مقروء بحالة `closed`) وينشئ فٌرصة جديدة بدلًا منها ضمن معاملة واحدة — راجع `features/opportunities/services/opportunities.service.ts § closeOpportunityAndCreateReplacement`.

## المهام المجدولة (Cron Jobs)

| المهمة | الوصف | الملف |
| --- | --- | --- |
| `close-expired-opportunities` | نقل الفٌرصة لحالة `expired` عند انتهاء موعد التقديم دون اكتمال المقاعد | `db/cron-jobs/close-expired-opportunities.sql` |
| `inactivity-nudge` | إرسال رسالة تحفيزية عند عدم دخول المستخدم لأكثر من 3 أيام (قابلة للإيقاف من إعدادات المستخدم) | `db/cron-jobs/inactivity-nudge.sql` |

تُجدوَل هذه عبر `pg_cron` مباشرة داخل Supabase (مجانية بالكامل)، ولكل مهمة أيضًا مسار API مطابق تحت `app/api/cron/*` يمكن استدعاؤه يدويًا للاختبار أو كخطة بديلة عبر Vercel Cron. **إغلاق الفٌرصة عند اكتمال القبول لا يحتاج مهمة مجدولة** — يحدث فورًا وذريًا داخل نفس طلب القبول (راجع `acceptance-lifecycle.ts`).

## معايير الأكواد (Conventions)

- **التسمية**: مجلدات وملفات بصيغة `kebab-case`، مكوّنات React بصيغة `PascalCase` داخل الملف.
- **التعليقات**: تعليق موجز فوق كل دالة أو مكوّن غير بديهي يشرح "لماذا" وليس "ماذا" (الكود نفسه يشرح "ماذا").
- **التحقق من المدخلات**: أي بيانات قادمة من المستخدم تمر عبر مخطط `Zod` في `features/*/validators/` قبل الوصول لقاعدة البيانات.
- **عدم تسريب منطق الأعمال للواجهة**: صفحات `app/` تستورد فقط، لا تكتب استعلامات قاعدة بيانات أو خوارزميات مباشرة.
- **الصور**: كل صورة مطلوبة في الكود تُوثَّق بتعليق (الوصف + المقاس + الصيغة) كما في دليل الصور أعلاه — قبل رفع أي أصل فعلي.
